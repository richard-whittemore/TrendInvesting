# Runbook: the Lightsail server (setup, restart, reconnect)

Provisioning for the live server in `docs/live-trading/plan.md` section 3: one Ubuntu 24.04 LTS VM running one IB Gateway (kept logged in by IBC), a shared market-data step, three engines (one per account, each with its own adapter client ID, ADR 0026 section 8), a reporter and a read-only dashboard, reachable only over Tailscale. Everything is in `deploy/`.

> **Status:** provisioning only. The engine is built and runs Boost in dry-run (`deploy/build-engine.sh`, below); the data step is built (`deploy/build-data.sh`, below; it writes the Boost engine's daily input, which the adapter delivers to the engine); the reporter, the dashboard and the owner's tools `operator` and `journal-query` are built beside the engine (`deploy/build-engine.sh`) and installed by `provision.sh services`. The IBKR adapter is built and tested against the fake gateway only (`ti-adapter-boost.service`, skipped until `provision.sh twsapi` and `provision.sh adapter` have installed `ibapi` and its code and `provision.sh services` has created its configuration; `docs/manual/paper-trading.md`, "Starting the adapter"; what is built is in `docs/manual/ibkr-adapter.md`). The engine and adapter units are skipped, not failed, until what they run is installed; the reporter's and the dashboard's fail with a message until theirs are, and the reporter's also until the Boost engine's `run.env` exists; the dashboard starts without it and shows a message until the engine has started a run. Nothing here has run against a real IBKR login. Trading mode defaults to **paper** and the API to **read-only** until the limited-live gate (AGENTS.md rule 5).

**Owner steps** are marked **[OWNER]**. Agents never sign up, pay or enter credentials.

## What is on the server

| Piece | Where | Notes |
|---|---|---|
| Users | `ti-gateway` (Gateway and IBC), `ti-trader` (data step, engines, adapter, reporter, dashboard), `ti-operator` (writes the owner's instructions into the operator inboxes; group `ti-trader`; no unit runs as it) | System users, no login shell. Engines never run as the user that can see the IBKR login. |
| IBKR login | `/etc/trend-investing/ibkr-login.env`, root:root 0600 | Outside the repository. Handed to `ti-gateway.service` only, through systemd `LoadCredential`. IBC's `config.ini` is rendered from it into a tmpfs on each start, so the password is never on disk beside the code, never in the journal, never committed. |
| Other secrets | `/etc/trend-investing/secrets.env`, root:root 0600 | The IRA account numbers, the Massive key, the reporter's `TI_NTFY_TOPIC`, `TI_NTFY_SERVER`, `TI_PAGERDUTY_ROUTING_KEY` and `TI_HEARTBEAT_URL`, and the Flex reader's `TI_IBKR_FLEX_TOKEN` and `TI_IBKR_FLEX_QUERY_ID`. The Boost account's number is not here (next row). Names only in `deploy/etc/secrets.env.example`. Handed to each unit as a private credential file (`LoadCredential`), never in its environment. |
| Each adapter's account | `/etc/trend-investing/accounts/boost.env`, root:root 0600 (directory 0700) | The Boost account's number alone (`IBKR_ACCOUNT_BOOST`), the only file its adapter is handed. Names only in `deploy/etc/accounts/boost.env.example`. |
| Programs | `/opt/trend-investing/bin/`: `ti-engine`, `ti-data`, `ti-reporter`, `ti-dashboard`, `operator`, `journal-query` | The server has no Go: each is built on the Mac and copied over (below). `operator` and `journal-query` are linked into `/usr/local/bin`, so `sudo -u ti-operator operator …` (an instruction: kill switch, clearance, acknowledgement), `sudo -u ti-trader operator approve …` and `sudo -u ti-trader journal-query …` work as the runbooks write them. |
| Engine settings | `/etc/trend-investing/engines/<instance>.env` | The account's label (`TI_ACCOUNT`), its client ID (`boost` 11, `trad-ira` 12, `roth-ira` 13; each must stay unique) and, for Boost, the start mode (`TI_MODE`). The data step uses Massive, not IB Gateway, and has none. |
| Gateway, IBC | `/var/lib/ti-gateway/Jts/ibgateway/1050`, `/opt/ibc` | Pinned and checksummed in `deploy/versions.env`. |
| State | `/var/lib/trend-investing/{data,engines/<instance>,reports,flex/<instance>}` | One journal and state directory per engine; each Flex reader's ledger of cash movements and its status file under `flex/<instance>`. |
| Firewall | `ufw`: deny inbound, allow only `tailscale0` | Lightsail's own firewall should also close port 22 once Tailscale works. |
| Updates | `unattended-upgrades`, security pocket only | No automatic reboot (a reboot logs the Gateway out). |

Schedule (New York time, `TZ` set in each unit): Gateway restarts nightly at 11:45 PM and does a full re-login every Sunday at 09:00 (`deploy/provision.sh` writes both to `/etc/trend-investing/gateway.env`). The data step runs weekdays 17:05, after the close plus its 60 settle minutes, and again at 18:05 and 20:05 (a no-op once the day is written); each account's Flex reader (`ti-flex@<instance>.timer`, once enabled) weekdays at 21:30; the Boost account's reporter (`ti-reporter@boost.timer`) every 5 minutes, around the clock, seven days a week, which is what makes its 30-minute repeats and 10-minute acknowledgement bound true at every hour (`docs/manual/alerts-and-dashboard.md`, "When the reporter runs"). ADR 0025 point 5 requires the nightly restart to fall after the day's reconciliation and outside trading hours: **confirm 11:45 PM against the real reconciliation time when the engines exist**, then change `TI_GATEWAY_RESTART_TIME`.

## Setup

1. **[OWNER] Create the Lightsail instance.** Ubuntu 24.04 LTS, x86_64 (not ARM: IBKR ships the Gateway for Linux x64 only), US East, the 2 GB plan (plan.md section 8), with your SSH key. Enable snapshots. This is a purchase; agents do not make it.
2. **[OWNER] Create the Tailscale account** and install Tailscale on your phone and laptop.
3. SSH in as `ubuntu` over the public address and fetch the repository (read-only checkout is enough): `git clone https://github.com/richard-whittemore/TrendInvesting.git`.
4. Run the first three stages. Each is safe to repeat:

   ```sh
   cd TrendInvesting
   sudo deploy/provision.sh base      # packages, users, auto-updates, Tailscale binaries
   sudo deploy/provision.sh gateway   # IBC and IB Gateway, checksum-verified
   sudo deploy/provision.sh services  # units, directories, empty root-only secret stubs
   ```

   Do not run these with `bash -x`.

   **On a server that already ran `provision.sh base`:** run `sudo deploy/provision.sh base` again after pulling a checkout whose `base` installs a package the server lacks. Today that is `tzdata-legacy`: IBKR states execution times in `US/Eastern`, which Ubuntu 24.04 ships only in that package. Without it the adapter refuses to start, saying the zone is not installed and naming the package and this step; so it is refused up front rather than starting and then stopping at the first execution report. `base` is safe to repeat.
5. **[OWNER] Join the tailnet:** `sudo tailscale up --ssh`, approve in the browser, then confirm you can reach the server by its tailnet name from your laptop.
6. Close the public door: `sudo deploy/provision.sh firewall`. It refuses (and says so) until Tailscale is signed in, so it cannot lock you out. Each run resets UFW, removing every existing rule (any added by hand included), then allows inbound on Tailscale only; re-add a manual rule after each run. Then **[OWNER]** remove the port 22 rule in Lightsail's Networking tab.
7. **[OWNER] Enter the IBKR login.** On the server: `sudo -e /etc/trend-investing/ibkr-login.env`, fill in `TWS_USERID` and `TWS_PASSWORD` (a paper-trading login first). Leave `TWS_TRADING_MODE=paper` and `TWS_READONLY_API=yes`. Never paste these into an issue, a PR, a chat with an agent or a shell command line. Enter the IRA account numbers, the reporter's ntfy topic (and your own ntfy server, if you run one) and PagerDuty routing key in `/etc/trend-investing/secrets.env` the same way, and the Boost account's number only in `/etc/trend-investing/accounts/boost.env` (`IBKR_ACCOUNT_BOOST=DU...`, no quotes, no spaces). A secrets file created by an earlier provisioner has `NTFY_URL=` and `HEALTHCHECK_URL=` lines, which nothing reads: replace them with the `TI_NTFY_TOPIC=`, `TI_NTFY_SERVER=` and `TI_PAGERDUTY_ROUTING_KEY=` lines of `deploy/etc/secrets.env.example`.
8. **[OWNER] Start the Gateway and approve 2FA:** `sudo systemctl start ti-gateway`. Approve the IBKR Mobile prompt on your phone within 3 minutes. Check `journalctl -u ti-gateway -n 50` shows a login and no credential.
9. **[OWNER] Set up your own ntfy server** (the daily summary goes only there; it carries balances, so never PagerDuty or the public ntfy.sh): once Tailscale works, `sudo deploy/provision.sh ntfy`. It installs the pinned, checksummed ntfy, listening only on the server's Tailscale address, and prints `TI_NTFY_SERVER=http://100.x.y.z:2586`. Put that line and an unguessable `TI_NTFY_TOPIC=` in `/etc/trend-investing/secrets.env` (`sudo -e`), and subscribe to the topic on that server in the ntfy app on a phone that keeps Tailscale on all the time (iPhone: "VPN On Demand"; Android: "Always-on VPN"). Then test a delivery end to end with a throwaway topic (`docs/manual/server.md`, "Your own ntfy server", steps 3 to 5). The server wakes the iOS app through ntfy.sh, which is told only a message's ID and a hash of its topic, never the message. Without it the summary is not sent (the reporter says so once, on the incident channels); incident alerts are unaffected.
10. **[OWNER] Set up the outside heartbeat** (required before paper trading): sign up at healthchecks.io, add a check with a period of 5 minutes and a grace time of 15 minutes, put its ping address in `/etc/trend-investing/secrets.env` as `TI_HEARTBEAT_URL=` (`sudo -e`), and add the PagerDuty integration on the Healthchecks side. The reporter pings it at the end of every clean firing; when the pings stop, Healthchecks pages you through PagerDuty. Test it by stopping `ti-reporter@boost.timer` for 20 minutes (`docs/manual/server.md`, "The outside heartbeat"). Without it, nothing outside the server notices the server dying.
11. Publish the dashboard to the tailnet only, once its binary is installed: `sudo tailscale serve --bg 8088` (**[OWNER]**, tailnet configuration). 8088 is the port the dashboard's unit listens on, on loopback.

**The data step.** Build it on the Mac from a clean checkout with `deploy/build-data.sh` (one Python file, `dist/ti-data`, standard library only; it refuses a dirty tree, is byte for byte the same for one commit, and `ti-data --version` prints the commit stamp), copy it to the server as `dist/ti-data` beside the `deploy/` folder, and run `sudo deploy/provision.sh services`, which installs it as `/opt/trend-investing/bin/ti-data`. Put the Massive key on the `MASSIVE_API_KEY=` line of `/etc/trend-investing/secrets.env` (`sudo -e`; a file created by an earlier provisioner has no such line: add it). Until the Boost engine's `run.env` exists the unit fails at each firing with a message naming it (never a silent skip); once it exists, run the warm-up once (`docs/manual/market-data.md`, "The daily data job") before the timer's first run. Install a new ti-data build only together with a fresh engine run and its warm-up, or after confirming it reproduces the current run's files: a build that encodes a delivered session differently stops the job (`docs/manual/market-data.md`, "A file already written differs").

**The engine, the reporter, the dashboard and the two tools.** Build them on the Mac from a clean checkout with `deploy/build-engine.sh` (linux/amd64, stamped by `scripts/build-stamp.sh` from `git describe --always --dirty`, and it refuses a dirty tree; the engine refuses dry-run, paper and live on an unstamped build). It writes `dist/ti-engine`, `dist/ti-reporter`, `dist/ti-dashboard`, `dist/operator` and `dist/journal-query`. Copy `dist/` to the server beside the `deploy/` folder and run `sudo deploy/provision.sh services` first: it refuses, installing nothing, if any program in `dist/` (`ti-engine` included) is not a Linux x86_64 program, so a Mac-side arm64 build (`--arch arm64`, built into its own folder with `--out`) can never be installed here. Then `sudo install -m 0755 dist/ti-engine /opt/trend-investing/bin/ti-engine`. `services` installs the other four, names any that is missing, and restarts the dashboard so it runs the new build. After an upgrade, check it did: `systemctl status ti-dashboard` shows it started after the install (if not, `sudo systemctl restart ti-dashboard`). The reporter needs no restart: it is started afresh at each firing and runs the new build at the next one.

**The reporter and the dashboard.** `provision.sh services` enables and starts `ti-reporter@boost.timer` (and `ti-data.timer`), and enables and restarts `ti-dashboard.service`, so they run without a reboot; it first stops and disables an earlier provisioner's single `ti-reporter.timer` and removes it. The reporter reads the Boost engine's current log, named by `TI_RUN` in `/var/lib/trend-investing/engines/boost/run.env`, so it fails with a message naming that file until the engine has been started once; it reads `run.env` again at every firing and follows a fresh run's new log by itself. The dashboard is given the engine's log folder (`-engine-dir`), finds the current run (the newest link of the chain of runs) on every request and follows the chain of runs back to the first (`docs/manual/alerts-and-dashboard.md`, "The history across restarts"), so a fresh run needs no dashboard restart; the restart in the upgrade step above is for a new dashboard build, which is why `provision.sh services` does it. The reporter fails, naming the line, until `secrets.env` holds its ntfy topic and PagerDuty key. Check each with `systemctl status ti-reporter@boost ti-dashboard` and `journalctl -u ti-reporter@boost`; `systemctl list-timers ti-reporter@boost.timer` shows the next firing. The IRA reporters are not enabled: the IRA engines have no configuration yet.

**The Flex reader.** `ti-flex@<instance>.timer`, one per account (`boost`, `trad-ira`, `roth-ira`), reads that account's deposits and withdrawals from IBKR's Flex Web Service once a weekday evening and writes each new one to `/var/lib/trend-investing/flex/<instance>/cash-movements.jsonl` (`docs/manual/reconciliation.md`, "Deposits and withdrawals, read from IBKR"). It runs the adapter's code (`provision.sh adapter`) and is skipped until that is installed; `provision.sh services` installs the templated unit `ti-flex@.service` and its timer `ti-flex@.timer` and creates each account's ledger directory, but enables **no** instance, since each fails at every firing until the token is in. To turn it on: **[OWNER]** in IBKR's Client Portal create the Flex query with the Cash Transactions section and generate a Flex Web Service token (the manual's "What you set up once"); put them on the `TI_IBKR_FLEX_TOKEN=` and `TI_IBKR_FLEX_QUERY_ID=` lines of `/etc/trend-investing/secrets.env` with `sudo -e` (a file created by an earlier provisioner has neither line: add them). Each instance reads its account's number from `/etc/trend-investing/accounts/<instance>.env` (root:root 0600): `boost.env` exists already; for an IRA fill in `IBKR_ACCOUNT_TRAD_IRA=<number>` in `trad-ira.env` or `IBKR_ACCOUNT_ROTH_IRA=<number>` in `roth-ira.env` (`sudo -e`; `provision.sh services` creates both with the line named only, so a reader started before it is filled fails naming the line), once that account's engine has run (its `run.env` is read too). Set the Flex query's period to *Last 30 Calendar Days* (the manual says why). The first reading must reach back to the New York day that account's first run was approved: enable the reader no later than 29 days after the approval day, so the first 30-day statement still starts on or before it; later, set a custom date range from the approval day for the first `start`, then set it back (otherwise the first reading stops as a coverage gap naming both days). Then, per account, `sudo systemctl start ti-flex@boost` once and check `journalctl -u ti-flex@boost` says it read (and `sudo cat /var/lib/trend-investing/flex/boost/cash-movements.jsonl.status.json` shows `"state": "read"`), and enable its timer: `sudo systemctl enable --now ti-flex@boost.timer`; for the IRAs, once their engines run, `sudo systemctl enable --now ti-flex@trad-ira.timer` and `sudo systemctl enable --now ti-flex@roth-ira.timer`, each after its own first `start` reads. When the token expires, generate a new one, replace the line, and start each enabled instance once the same way.

**The engine's unit.** `provision.sh services` installs `boost.env` (`TI_MODE=dry-run`) and `boost.config` (mode `dry-run`). The engine units are **not enabled**, and `provision.sh services` disables any engine instance an earlier provisioner enabled: every start is an explicit owner step, written down in `docs/runbooks/durable-log.md`, "Restarting an engine". The unit runs the engine with `-mode`, `-config`, `-socket /run/ti-engine-<instance>/engine.sock` (a 0700 directory per engine), `-log`, `-out` and `-as-of`, from the account's `run.env`, and never restarts it by itself (`Restart=no`).

## Restart drill

Rehearse before any engine trades. Record the result in #329.

1. `sudo systemctl restart ti-gateway`. Expect a re-login within about two minutes. If the session was fresh, no phone prompt; after a cold start expect one **[OWNER]**.
2. Confirm the Gateway is up: `systemctl is-active ti-gateway` and `journalctl -u ti-gateway --since "5 min ago"`.
3. A Gateway restart does not restart an engine: the engine keeps running, and its adapter reconnects and matches IBKR again before sending anything (`adapter/ibkr/loop.py`). Confirm each engine that was running is still `active` and that its journal shows a reconcile after reconnecting, not a resume from stale state (ADR 0019 and 0025 point 5: a restart must not cross an open order).
4. `sudo reboot`, then repeat 2. This one needs your phone **[OWNER]**. Schedule reboots for Sunday, after the weekly cold restart, so one prompt serves both. The engines stay stopped after a reboot (they are not enabled): start each by `docs/runbooks/durable-log.md`, "Restarting an engine" (a reboot is not a crash, so each is a fresh run the owner approves).
5. Kill one engine (`sudo systemctl kill --signal=SIGKILL ti-engine@boost`). Confirm the other two stayed `active` and that boost stays **stopped** (`Restart=no`): a fault touches one account only (ADR 0026 section 8), and only the owner restarts it. Within about a minute you are paged that `ti-engine@boost.service` failed (`ti-unit-failed@`, `docs/manual/server.md`, "A failed unit"), naming the engine's last journal line; the reporter's next firing does not page it again. `systemctl list-units --all 'ti-unit-failed@*'` shows `ti-unit-failed@ti-engine@boost.service.service`, and `/var/lib/trend-investing/reports/unit-failures.json` holds the key `unit-failed:ti-engine@boost.service/<run>`, where `<run>` is `systemctl show -p InvocationID --value ti-engine@boost`. Resume it as a crash by the runbook. Left failed past 20 minutes, the engine also takes the outside heartbeat's check down (no firing that finds a trading unit failed pings it), and Healthchecks pages you too; that page clears at the first clean firing after the engine is running again.

## Reconnect drill: the Gateway will not log in

1. `journalctl -u ti-gateway -n 100` and the IBC log in `/var/log/ti-gateway/`. Look for a 2FA timeout, bad credentials or "existing session".
2. **2FA timed out:** the unit restarts IBC and sends a new prompt every 30 s plus the timeout. **[OWNER]** approve it on the phone.
3. **Existing session detected** (you logged in to IBKR from the app or website): IBC is set to `manual`, so it waits rather than fighting for the session. Log out of the other session, then `sudo systemctl restart ti-gateway`.
4. **Bad credentials:** do not retry in a loop (IBKR locks the login). `sudo systemctl stop ti-gateway`, **[OWNER]** correct `/etc/trend-investing/ibkr-login.env`, start again.
5. Until the Gateway is back, engines hold: they must not trade without it. Follow `docs/runbooks/reconciliation.md` if any account left Normal. Never edit numbers to repair a state.

## Bumping a pinned version

Every download in `deploy/versions.env` is verified by SHA-256 and provisioning stops on a mismatch.

- **IBC:** release and asset at `https://github.com/IbcAlpha/IBC/releases`. The release publishes no checksum, so compute it yourself from the downloaded asset and say so in the PR.
- **IB Gateway:** IBKR's stable installer link is a moving target and publishes no checksum; the version is read from `https://download2.interactivebrokers.com/installers/ibgateway/stable-standalone/version.json`. When the file changes, provisioning fails closed. ADR 0025 point 5: repeat the paper-account execution-coverage test on the new version first, then change `GATEWAY_BUILD`, `GATEWAY_MAJOR` and `GATEWAY_SHA256` together.
- **TWS API (`ibapi`):** IBKR's download page, `https://download2.interactivebrokers.com/installers/tws-api/index.html`. Only the "Latest" Mac/Linux build includes the Python API, so the pin is Latest; its link is a moving target and publishes no checksum, so compute the SHA-256 of the downloaded installer and say so in the PR. `sudo deploy/provision.sh twsapi` fetches and verifies it, as its own step (not part of `all`, so it never blocks the Gateway or the services); once verified, the same step installs its Python client into the adapter's own environment (`/opt/trend-investing/adapter-venv`) and writes `/opt/trend-investing/twsapi/INSTALLED`, which the adapter checks against the pin installed with its code (`provision.sh adapter`) and refuses to start on a difference. Because the link moves, `provision.sh twsapi` stops with a checksum mismatch whenever IBKR publishes a new build there, even though nothing in `versions.env` changed. That is the fail-closed stop working, not a fault: the build the adapter was tested on is no longer at that link. Do not edit the checksum to match; treat it as a version bump (below). ADR 0025 point 5: repeat the paper-account coverage test on the new version first, then change `TWSAPI_VERSION` and `TWSAPI_SHA256` together, and with them the same release's Mac/Unix archive pin, `TWSAPI_ARCHIVE_URL` and `TWSAPI_ARCHIVE_SHA256` (the arm64 path, `docs/manual/mac-mini.md`): its file name carries the version (`twsapi_macunix.<major><minor>.<micro>.zip` under `https://interactivebrokers.github.io/downloads/`), its `IBJts/API_VersionNum.txt` must name the same version, and its SHA-256 is computed from the download as the installer's is.
- **protobuf:** `ibapi` imports it; the pin is PyPI's pure-Python wheel (`protobuf-<version>-py3-none-any.whl`, one file for amd64 and arm64). Take the file's SHA-256 from `https://pypi.org/pypi/protobuf/<version>/json` and check it against the downloaded file. Move the pin only to the version the TWS API build in use requires, and change `PROTOBUF_VERSION`, `PROTOBUF_URL` and `PROTOBUF_SHA256` together. `provision.sh twsapi` verifies it with the installer, before anything is installed.
- **Tailscale:** `https://pkgs.tailscale.com/stable/`, with the checksum from the `.sha256` file beside the tarball.

## What was rehearsed, and what was not

Run `deploy/rehearse.sh` (Docker, a clean Ubuntu 24.04 container; about 350 MB of downloads). On 2026-10-16 it passed on an Apple-silicon Mac, in a native arm64 container (and again on 2026-10-18 with the reporter, dashboard and tool checks below), because linux/amd64 containers would not start under Docker Desktop there. Set `TI_REHEARSAL_PLATFORM=linux/amd64` on an x86_64 host to run the Gateway installer as well. It checks:

- the full provisioning pass runs twice and the second pass changes nothing and does not overwrite an owner-entered secret stub;
- the real pinned IBC, IB Gateway and Tailscale downloads match their checksums; IBC and Tailscale are installed;
- `provision.sh ntfy` fetches the pinned ntfy against its checksum (a mismatch is refused, nothing installed), refuses every address outside Tailscale's `100.64.0.0/10`, and writes a configuration that listens on the one Tailscale address only; the reporter's stand-in run starts from a state file recorded before the fixture log, as a server's would be;
- a corrupt cached download is not trusted;
- `provision.sh twsapi` installs the pinned protobuf wheel and IBKR's `ibapi` into the adapter's own environment, `ibapi` imports there (version 10.51.01, protobuf 5.29.5), and the adapter's pin check accepts the install record (which names `TWSAPI_ARTEFACT=installer`; on x86_64 the adapter accepts only that, and refuses an older record without the key with "reinstall"); a protobuf wheel that differs from its pin is refused with no environment or record written, or the existing ones left unchanged (rehearsed 2026-10-20 in a linux/amd64 container; an arm64 container cannot run the x86_64 TWS API installer, so there the downloads are only verified);
- the service users are non-root with no login shell; secret files are root:root 0600;
- the credential renderer writes a fake password (with special characters) verbatim to a 0600 file, prints no credential, and leaves no copy under `/etc` or `/var/log`; it refuses an empty login and an unknown trading mode; the gateway's start exits 78 on an empty login, which the unit does not restart on;
- the reporter, the dashboard, `operator` and `journal-query` are installed from the build; `journal-query` and `operator approve` run as `sudo -u ti-trader`, and instructions are recorded as `sudo -u ti-operator operator ...` (as `ti-trader` they are refused); the old single reporter's timer, service and timer link are removed;
- `ti-unit-failed@.service` is installed and verified with the other units (`systemd-analyze verify`, under the names `OnFailure=` gives it for the engine, the adapter and the reporter, such as `ti-unit-failed@ti-engine@boost.service.service`), its command line is run as `ti-trader` with the system's own `journalctl` (no journal is kept in that container, so the reason says the run wrote no line) against the stand-in channels, with the failed run named as systemd names it, pages once per failure episode and sends nothing on a second run for the same failed run, and the engine, adapter and reporter units each name it in `OnFailure=`; the reporter's own run asks a stand-in `systemctl` for the engine's and the adapter's state (no systemd runs there) and passes the stand-in heartbeat endpoint a ping;
- in a second container with systemd as PID 1 (`deploy/rehearsal/inside-systemd.sh`; not privileged: it runs systemd as the Mac mini container does, every capability dropped but the eleven `deploy/mac-mini/up.sh` names, a cgroup namespace of its own remounted writable, Docker's default seccomp filter kept), a stand-in engine with the real engine unit's `OnFailure=` line fails and systemd itself starts `ti-unit-failed@ti-engine@boost.service.service`, whose `%i` is `ti-engine@boost.service` (the hook writes it to a file) and whose `MONITOR_INVOCATION_ID` is the failed run's; the built reporter pages both stand-in channels with the run's own last line, keyed by that run; restarted and failed again with no reporter firing between, it is one failure episode: no second page and the first incident left open; after the episode ends (the record cleared, as a firing that sees the unit well would) a run that wrote nothing pages again with systemd's "Failed with result" line as the reason, never journalctl's "-- No entries --"; in a new episode a start refused for a missing `EnvironmentFile` pages with systemd's "Failed to load environment files" line; `systemctl start` of the exact hook name pages nothing new; `systemctl show` as `ti-trader` names the failed run; and a start refused while the unit is already failed is shown to start no hook (systemd 255), which is why the reporter's firing checks too. systemd's credential directory is not mounted in a Docker container, so there the hook reads a copy of the secrets (`LoadCredential=` itself is checked by `systemd-analyze verify`);
- the reporter, run with its unit's own command line (expanded as systemd would) as its unit's user `ti-trader`, on files owned as on the server, against a durable log the engine wrote, reads its secrets from the credential file only, delivers to a stand-in ntfy and PagerDuty on loopback, writes its state file, and sends nothing again on a second run;
